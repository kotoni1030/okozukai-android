# 実装計画

各段階は小さく動作確認できる単位にする。2026-11-17時点でP0・P1の基本実装と検証を完了。P2〜P6の主要機能も実装し、JVM単体試験6件・エミュレーター試験6件を実行。P3の実際のSAF入出力と障害試験、P7の実機・アクセシビリティ・性能確認等は残作業。全受入条件を合格済みとはしない。詳細は [toolchain.md](toolchain.md) を参照。

| 段階 | 作るもの | 完了の判断 |
|---|---|---|
| P0 環境 | Gradle、Compose、Room、テスト基盤、バージョン記録 | 空画面のビルド・起動。実機/エミュレーターと未確認事項を記録 |
| P1 最初の記録 | カテゴリ初期値、支出入力、保存、履歴 | 650円の支出を追加し、再起動後も同じ内容が見える |
| P2 日々の利用 | 収入、取引編集・削除、月移動、ページング | 収支を修正すると一覧と合計が一致。月境界も正しい |
| P3 バックアップ | JSON DTO、検証、書き出し、全体復元 | 新しいDBへ復元して同じデータ。失敗時に既存DBを保持 |
| P4 振り返り | 月別・カテゴリ別集計と横棒グラフ | 既知のデータで合計・割合が正しい |
| P5 予算 | 月全体、カテゴリ予算、前月コピー | 未設定・0円・超過を区別。コピーが原子的に完了 |
| P6 貯金目標 | 複数目標のCRUDと現在積立額 | 達成判定が正しく、収支には影響しない |
| P7 仕上げ | オフライン、アクセシビリティ、性能、利用手順 | 受入試験と実機確認の結果を提示 |

## P0：環境確認

`architecture.md` に従う。JDKやSDKのインストール有無とサポート範囲を調べる。開発者に分からない値をいきなり選ばせず、互換性に基づく安定構成を提案・記録する。アプリのapplicationIdと署名を変えると既存インストールへの更新に影響するため、日常利用版を入れる前に確定する。

成果物：起動できるプロジェクト、Version Catalog、READMEの環境手順、`docs/toolchain.md`。この時点で未使用の画面やクラウドSDKを追加しない。

## P1：支出を記録して残す

最初からv1の全テーブルと制約を作っておく。予算・目標の画面はまだ作らなくてよいが、バックアップv1の形とRoom schemaを一致させる。初期カテゴリをDB新規作成時だけ投入する。

入力からRepositoryを通して保存し、履歴へ反映。金額入力、二重タップ、保存失敗、回転を確認する。説明では「Compose＝画面」「ViewModel＝画面状態」「Room＝保存」の対応を示す。

## P2：継続利用に必要な操作

収入、編集、削除、月選択、日付単位の合計と履歴ページングを完成させる。仕組みを共通化し、収入と支出の画面をほぼ同じコードで二重に持たない。

## P3：データを持ち出して戻す

日常の本物の記録を溜め始める前に完成させる。P1で作った未使用テーブルも配列として出力し、v1形式を今後変えずに使えるようにする。既存の例JSONを読み込めること、検証失敗時にDBが変わらないことを確認する。

正しいファイル、未知バージョン、不足フィールド、不正参照、重複キー、ストレージ不足、入力取消、書込途中の失敗を検証する。OSバックアップ除外もこの段階で設定する。

## P4〜P6：集計・予算・目標

表示値の計算は先にテスト可能な形で作り、既知の期待値を確認してから画面に組み込む。グラフ専用の巨大なライブラリを最初から入れない。貯金目標の手動積立と取引の収支が二重計上されないことを確認する。

## P7：初期版の完了

`acceptance-tests.md` の自動・手動チェックを実行。実機の機種、OS、ビルド種類、性能計測値を記録する。未確認項目は未確認のまま一覧化し、検証結果を捏造しない。

READMEに利用開始、APKのインストール/更新、バックアップ、復元、開発の起動手順を追記する。配布用署名鍵や実データのJSONは成果物に混ぜない。

## 初期版の後

カテゴリの変更希望、実際に入力で面倒だった点、必要な表示を利用者から聞く。ショートカット、カテゴリ編集、入力テンプレート、OCR、同期は、必要なものを個別に採用する。初期版の完成前に一括で積み増さない。
